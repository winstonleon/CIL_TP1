| Respuesta de n8n | Cuándo |
|---|---|
| 202 `{ "estado": "recibido" }` | Cuerpo válido. Se responde antes de procesar (S7) |
| 400 `VALIDACION` | Cuerpo inválido. Es definitivo y la API no reintenta |
| 403 | Secreto ausente o incorrecto |

Todos los datos se piden a `/internal/*` con la credencial `cil-api-interna`.

### Endpoints internos nuevos (n8n → API, `requireTokenServicio`)

**`POST /internal/expedientes/:id/carpeta-informativa`**: reserva el envío y arma el mensaje (C27 b). En una transacción:
1. Bloquea el expediente (`FOR UPDATE`).
2. Exige `estado = 'prospecto'`.
3. Busca la notificación `correo`/`carpeta_enviada` del expediente.
4. Si no hay ninguna, inserta una `pendiente`. Si hay una `pendiente` cuyo último intento (`fecha_envio`) fue hace más de 10 min, **la retoma**: mismo `id_notificacion` y `fecha_envio = now()` (S4, D7).
5. Arma el asunto y el cuerpo.
```json
201 { "id_notificacion": 41, "tipo_evento": "carpeta_enviada",
      "asunto": "Carpeta informativa · Admisión 2027",
      "cuerpo": "Hola, María Fernanda:\n\n[Presentación de la carpeta informativa: por definir con el colegio]\n\nGrado de interés: 3.° de primaria\nCarpeta informativa: [Enlace a la carpeta informativa: por definir con el colegio]\nAgenda tu visita guiada: http://localhost:5173/visita-guiada?t=v1.q3Jx…\n\n[Datos de contacto de Admisión: por definir con el colegio]" }
```
- 409 `CARPETA_YA_REGISTRADA`: hay una fila `enviado` o `fallido`, o una `pendiente` intentada hace menos de 10 min.
- 409 `ESTADO_NO_PERMITE_CARPETA`: el expediente no está en `prospecto`.
- 404 si el expediente no existe; 400 si el id es inválido.

**`PATCH /internal/notificaciones/:id`** `{ "estado_envio": "enviado" | "fallido" }` → 200 `{ "id_notificacion", "estado_envio" }`.
- De `pendiente` pasa al estado pedido y pone `fecha_envio = now()`.
- Repetir el mismo valor responde 200 sin cambios.
- Pasar de un estado cerrado a otro responde 409 `NOTIFICACION_CERRADA`. Si no existe, 404.
- **`fallido` solo se pide ante el rechazo permanente del destinatario (D7).** Un error técnico no llama a este endpoint: la fila queda `pendiente`.

**`GET /internal/captacion/pendientes`** → `{ "expedientes": [ { "id_expediente": 12 } ] }`. Lista solo ids, con un máximo de 20 y los más antiguos primero. Incluye los expedientes en `prospecto` que:
- no tienen carpeta y se registraron hace más de 1 min; o
- tienen una carpeta `pendiente` intentada hace más de 10 min. Esto incluye los errores técnicos de D7.

**`POST /internal/notificaciones/:id/rebote`** `{ "origen": "smtp_rechazo" }` → 200 `{ "id_notificacion", "estado_envio": "fallido", "transicion": true|false }`. En una transacción (R6):
1. Bloquea la notificación. Si no es `correo`/`carpeta_enviada` → 409 `NO_ES_CARPETA`.
2. La deja en `fallido`.
3. Inserta `notificacion_rebotada` (`id_personal` nulo; `detalle { id_notificacion, canal, origen }`).
4. Si el expediente está en `prospecto`: `transicionarExpediente(prospecto → contacto_no_entregado, idPersonal: null, detalle { motivo: "rebote_carpeta", id_notificacion })`.

Si el rebote ya está registrado, responde 200 con `transicion: false` y no inserta nada (S3).

**`POST /internal/errores-flujo`** `{ "flujo", "nodo", "id_ejecucion" }` → 204 (C2).
- Usa `.strict()`, sin campo de mensaje.
- Solo escribe en el log: `Fallo en n8n (flujo=…, nodo=…, ejecución=…)`.

## 2. Diseño

### Enlace para agendar la visita (D3, sin cambios)
- **Módulo:** `api/src/crypto/enlaceVisita.ts`, con `crearTokenVisita(id)` y `leerTokenVisita(t) → id | null`.
- **Formato:** `v1.` + base64url(iv de 12 B ‖ AES-256-GCM(id en 4 B) ‖ tag de 16 B), con AAD `"enlace-visita"` y clave `ENLACE_VISITA_KEY`.
- **URL:** `${FRONTEND_PUBLIC_URL}/visita-guiada?t=<token>` (S6).
- **Vigencia:** el token no vence. HU0003 decide qué estados lo aceptan y si vence (C31).
- **Si HU0003 aún no existe:** el enlace se envía igual. En dev abre una página en blanco, porque el router no tiene ruta comodín. No hay página provisional ni despliegue antes de HU0003.

### La carpeta informativa (sin cambios)
- **Módulo:** `api/src/services/carpetaInformativa.ts`, versión `borrador-1`. Lo del colegio va entre corchetes.
- **URL:** variable `CARPETA_INFORMATIVA_URL`, opcional. Si está vacía, el cuerpo lo dice entre corchetes.
- **ADR-12 (Drive):** no depende de él. Es un enlace, no un adjunto ni una integración.

### `captacion` (`n8n/workflows/captacion.json`, vía `constructor-n8n`)
1. **Entrada A:** Webhook `captacion` (`headerAuth`, `responseMode: responseNode`) → «Validar evento».
   - Si es válido → Responder 202 → *Procesar*.
   - Si no → Responder 400 → Stop and Error.
2. **Entrada B (C27 a):** Schedule Trigger cada 1 min → GET `/internal/captacion/pendientes` → un ítem por expediente → *Procesar*.
3. **Procesar:**
   - POST «Reservar carpeta» (`retryOnFail`).
   - Un 201 → Execute Workflow `notificacion-multicanal` con `{ id_expediente, tipo_evento: "carpeta_enviada", asunto, cuerpo, id_notificacion }` y `onError: continueErrorOutput` (C9).
   - Un 409 → NoOp «Sin acción».
   - Cualquier otro error → Stop and Error.
4. **Según el resultado de `notificacion-multicanal`:**
   - `rechazo_destinatario` → POST `/rebote` (2.0).
   - `error_tecnico` → Stop and Error «captacion: envío pospuesto por un error técnico del correo (expediente N, notificación M)». Se registra en `registro-errores` y la fila queda `pendiente` (D7).
   - `enviado` → termina.
5. **Rama de error de `notificacion-multicanal` (C9).** Un Code «Clasificar fallo de la notificación» separa los casos según el contrato de `notificacion-multicanal` (`VALIDACION`, `CONTACTO_NO_DISPONIBLE` o cualquier otro). `constructor-n8n` fija cómo se lee el código del error que llega al Execute Workflow, sin cambiar lo que verifican S0-C7 y S0-C8.
   - **400 o 502 (deterministas, D7):** PATCH `fallido` (un 409 cuenta como ya cerrada), sin rebote ni transición. Stop and Error → `registro-errores`. No se reintenta, porque el barrido no toma las `fallido`.
   - **500 u otro error:** sin PATCH, la fila queda `pendiente`. Stop and Error → `registro-errores`. El barrido la retoma a los 10 min.
   - En los dos casos, el expediente sigue en `prospecto`.
6. **`settings`:** `errorWorkflow: "registro-errores"` (resuelto por nombre), `saveDataSuccessExecution: "none"` y `executionOrder: "v1"`.

### Cambios a `notificacion-multicanal` (compatibles; S0-C7 y S0-C8 sin tocar)
- **Entrada opcional `id_notificacion`.** Sin ella todo sigue igual: cualquier error de envío inserta `fallido` (contrato de S0-C3 y S0-C7).
- **Con `id_notificacion`, un Code en la rama de error de «Enviar correo» separa dos casos:**
  - **rechazo permanente del destinatario** (5xx en RCPT, p. ej. «all recipients were rejected: 550…») → PATCH `fallido` y `correo.rechazo_destinatario = true`;

- `constructor-n8n` fija los patrones contra los errores reales que n8n recibe de Mailpit: un 550 con `MP_SMTP_ALLOWED_RECIPIENTS` y la falta de conexión con Mailpit detenido.
